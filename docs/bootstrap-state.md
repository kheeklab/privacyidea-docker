# Bootstrap and schema startup restrictions

Automatic bootstrap is unavailable for every backend and topology. A markerless, interrupted, or unknown installation stops without creating accounts, keys, schema, or a completion marker. Do not use skip mode as automatic recovery or adoption.

For guarded startup with an existing completion marker, the database must have the exact installed image's Alembic head revision set and pass the available read-only checks. PostgreSQL, MySQL, and MariaDB guarded startup is unavailable while catalog visibility remains unqualified. SQLite checks include integrity, expected model tables and columns, and key-file format; they cannot establish that the encryption key belongs to the database or that an account is healthy. Custom key modules and other valid configurations may be rejected.

Guarded SQLite inspection copies the database into memory without opening the persistent database through SQLite. It rejects WAL-mode databases, any existing `-wal`, `-shm`, or `-journal` sidecars (including empty or stale files), databases larger than 67,108,864 bytes, hard-linked or non-regular inspected files, files that cannot be opened with `O_NOATIME|O_NOFOLLOW`, and snapshots that change while read. The runtime and filesystem must support these Linux flags and semantics; the guard has no ordinary-read fallback. These restrictions can prevent existing installations from starting.

Stop and externally fence every other database writer before preflight. Keep the database quiescent and do not replace it or alter sidecars from preflight through service handoff. The snapshot check is not a lock, writer fence, or database/key binding, and the container cannot enforce this prerequisite. If quiescence cannot be assured, treat the topology as unqualified. `PI_SKIP_BOOTSTRAP=true` does not remediate these restrictions or certify state. Preserve all files and seek a separately qualified process when inspection fails.

With `PI_AUTO_UPDATE=true`, a guarded initialized installation at the verified image head starts without invoking a migration. Any non-head or uncertain state is rejected. No automatic schema upgrade is currently qualified, and this is a compatibility restriction for existing installations. Before changing image or schema, retain a consistent database, encryption and audit keys, and configuration-secret backup. Use only a schema-compatible image and a separately qualified migration process; this document does not provide a verified migration or recovery command.

`PI_SKIP_BOOTSTRAP=true` with `PI_AUTO_UPDATE=false` is an operator-selected external-provisioning bypass. It does not certify database, key, account, schema, or readiness state. Combining `PI_SKIP_BOOTSTRAP=true` with `PI_AUTO_UPDATE=true` is rejected before hooks, configuration writes, or server startup.

Changing `PI_ADMIN_USER` or `PI_ADMIN_PASSWORD` on an existing installation does not change its administrators. Do not delete databases or key volumes to reset accounts. Key format, matching audit keys, a marker, and a matching revision do not prove database/key identity. Markerless adoption and credential recovery remain unqualified and are not automated.
